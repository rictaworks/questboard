# リリース規程

questboard のリリース手続を定める。**本書がリリースに関する判断尺度の正である。**

## 1. リリースの起点

**GitHub Release の発行が本番デプロイの起点である。** main へのマージだけでは本番は動かない。

`.github/workflows/release-deploy.yml` が Release published をトリガーに、Railway backend / sync-server → Vercel frontend の順にデプロイする。

タグは**注釈付きタグ**（annotated tag）とする。軽量タグはタガー・日時・メッセージを持たず、誰がいつ切ったのかを後から読めない。

```bash
git tag -a vX.Y.Z -m "<変更の要旨> (#<Issue番号>)"
git push origin vX.Y.Z
gh release create vX.Y.Z --title "vX.Y.Z <表題>" --notes-file <ノート>
```

## 2. 版番号の刻み

`vX.Y.Z` の形式とし、増分は次の意味を持つ。**判断は本節のみを尺度とする。**

| 位置 | 増やす条件 | 例 |
|---|---|---|
| メジャー（X） | 利用者の操作、共有URLの形式、保存済みボードの互換性が壊れる変更 | （実績なし） |
| マイナー（Y） | 機能の追加、または利用者に見える動作が変わる変更 | v1.1.0（フォロワー判定の委譲）、v1.2.0（セッションの有効期限） |
| パッチ（Z） | 不具合の修正のうち、利用者に見える動作の意図が変わらないもの | v1.1.1（待機の応答が誤っていた）、v1.2.1 相当 |

**「動作が変わる」かどうかは利用者から見て判断する。** 内部実装だけが変わり、画面と応答が同じならパッチとする。

文書のみの変更、テストのみの変更では版を発行しない。次のリリースに含める。

## 3. 添付物

**Release に成果物を添付しない。** questboard の Release はデプロイの起点であり、配布物ではない。利用者が受け取るのは稼働中のサイトであって、ダウンロードするファイルではない。

したがって次を行わない。

- ビルド成果物（アーカイブ・バイナリ）の添付
- チェックサム一覧（`SHA256SUMS` 等）の公開

GitHub が自動生成するソースの tar/zip は、この規程における添付物として扱わない。

**この方針を変える場合は本節を先に改訂する。** 添付物を伴うリリースは、チェックサムの生成と公開を同時に定めなければならない。

## 4. リリース前に通すもの

Release を発行する前に、次を実施する。

| 手続 | 内容 |
|---|---|
| CI | 必須ステータスチェックがすべて通っていること |
| `release-security-gate` | 差分モードで工程 B〜G。**「未実施」が残る状態でリリースしない** |
| `release-audit` | 直近の公開済みリリースタグを比較基準とする差分監査 |

**版を発行するたびに実施する。** 「小さい修正だから」を理由に飛ばさない（2026-08-25 に v1.1.1〜v1.2.0 で飛ばし、後からまとめて回収した）。

監査が Major を返した場合、是正してから公開する。公開後に気づいた場合はリリースノートを訂正する。

## 5. リリース後に行うもと

| 手続 | 内容 |
|---|---|
| 本番ユーザーテスト | 変更が利用者に見える形で効いていることを、本番のブラウザで確認する |
| `code-review` | 当該リリースの差分に対して実施する |

**本番ユーザーテストは実測をもって完了とする。** 「CI が通ったから動いているはず」は完了ではない。2026-08-25 のリリースでは、CI が全て緑のまま本番で2件の不具合（待機が 502 になる・照会用IDが画面に出ない）が見つかっている。

## 6. リリースノート

- 当該版に含まれる**すべてのマージ済み PR** を反映する。文書のみの変更も記載する
- 利用者に見える動作が変わる場合、変わる内容を「変わること」として明示する
- 残る制約がある場合は隠さずに書く
- 運用の変更（環境変数の追加・削除、定期実行の増減）を書く
