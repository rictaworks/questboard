# PR #148: apply_op のrescue範囲不具合(#121)に対する回帰テストを追加

- PR: https://github.com/rictaworks/questboard/pull/148
- 対応issue: https://github.com/rictaworks/questboard/issues/121

## 非エンジニア向けユーザーテスト手順

この修正は画面の見た目や操作方法を一切変更しません。バックエンドのサーバー内部処理（送られてきたデータの形式が不正なとき・想定外のエラーが起きたときに、サーバーがどんなエラーメッセージを返すか）だけを直すものなので、実際の確認は「サーバー側のテストプログラムを動かして、結果が正しく表示されるか」を見る形になります。

### 事前に必要なもの

- このリポジトリを開発用に動かせるPC（Docker Desktop がインストール済みであること）
- 特別なパスワードやAPIキーは不要です

### 手順

1. パソコンで「ターミナル」（黒い画面の操作アプリ。Macなら「ターミナル」、Windowsなら「PowerShell」）を開きます。
2. 次のコマンドを1行ずつコピーして貼り付け、Enterキーを押します。これはテスト用のデータベースを起動する準備です。

   ```
   cd questboard
   docker compose up -d postgres
   ```

3. データベースが起動したら（数秒待ってください）、次のコマンドを貼り付けてEnterキーを押します。これがこのPRで追加・修正したテストをまとめて動かすコマンドです。

   ```
   cd src/backend
   bundle exec rspec spec/requests/object_ops_spec.rb -e "rejects string-valued text_crdt retain/delete counts with a field-specific message" -e "does not relabel an unrelated TypeError from later in apply_op as a lamport_ts validation error"
   ```

4. 画面に緑色の文字で

   ```
   2 examples, 0 failures
   ```

   という行が表示されれば合格です。これは以下の2点が確認できた、という意味です。
   - 不正な形式のデータ（文字列の`retain`/`delete`）を送ったときに、サーバーが正しいエラーメッセージ（『lamport_ts が整数ではありません』という無関係な文言ではなく、実際に問題のある項目を指すメッセージ）を返している
   - `lamport_ts` の変換とは無関係な場所で予期しないエラーが起きた場合に、そのエラーが「lamport_ts が整数ではありません」というメッセージにすり替えられず、正しくエラーとして検出されている（＝サーバーの不具合を隠さずに検知できる）

5. もし `failures` の数が0以外だったり、赤い文字でエラーが表示された場合は、この修正がうまく機能していない可能性があるため、開発担当者に画面のスクリーンショットを添えて報告してください。
